# 锦鲤签 · 好运倒计时 —— 项目协作规则

适用范围：Demowall 参赛作品「锦鲤签 · 好运倒计时」的全部协作过程。
来源说明：本规则由 PinWeb 项目协作规则裁剪改造而来，移除多仓契约、后端部署、知识库版本轨等与单文件前端 Demo 无关的部分，保留门禁串行、文档归档、强制首读、命名规范与修订记录。

---

## 一、核心原则

1. **门禁串行不可跳步**：需求 → 设计 → 开发 → 测试 → 上线，上一阶段未经用户显式确认，不得进入下一阶段。
2. **文档统一归档**：所有协作产物写入 `.trae/documents/`，禁止散落在工作区根目录。
3. **记忆先行**：每次协作先按 §二 强制首读 SOP 执行，发现认知缺口先补记忆再动手。
4. **演示优先**：本项目是现场 Demo，功能取舍以「现场 30 秒内能被感知」为第一标准，其次才是可玩深度。
5. **极简交付**：单文件 HTML、零外部依赖、零网络请求；不为假想需求引入复杂度。
6. **代码注释**：生成的代码必须带函数级中文注释。

---

## 二、AI 强制首读 SOP

每次协作（新会话或续作）第一步必须：

1. `Read .trae/documents/project_memory.md` → 取当前版本号与已确认决策
2. `Read .trae/documents/plan.md` → 确认当前阶段、已定稿范围与待确认项
3. 若历史摘要/上下文与现行文档冲突，以现行文档为准
4. 发现需求不在项目记忆中 → 先起草补充条目，用户确认后落盘，再执行任务
5. 明确当前阶段后，按 §四 门禁推进；越级时主动提醒用户

---

## 三、文档结构

文档根目录 `.trae/documents/`，采用扁平结构（单版本 Demo 不需要版本文件夹），由文件头标注版本号：

```
.trae/
├── rules/
│   └── project_rules.md          本规则（只写门禁与红线）
└── documents/
    ├── project_memory.md         项目记忆：定位、约定、已确认决策、踩坑（AI 必读）
    ├── plan.md                   计划：需求描述 + 执行计划（活文档，滚动更新）
    ├── design.md                 设计：视觉与交互方案（增量，承接计划）
    ├── dev_log.md                开发日志：按任务记录改动与自测结论
    ├── test.md                   测试：用例 + 报告
    └── release.md                更新说明：交付方式、演示脚本、回滚
```

文档分工边界：

- **规则文件**只写「什么时候做什么、什么不能做」；
- **项目记忆**只写「是什么、为什么、踩过什么坑」，具体参数与数据约定写在这里；
- **计划文档**只写「这次做什么、做到什么程度、按什么顺序做」；
- 代码能直接看出来的实现细节，不写进任何文档。

## 四、五阶段流转

| 阶段 | 准入 | 产物 | 准出 |
|---|---|---|---|
| 需求 | 用户提出需求 | `plan.md`（需求描述 + 执行计划） | 计划定稿，用户确认 |
| 设计 | 计划定稿 | `design.md`（配色、版式、动效、交互状态） | 设计定稿，用户确认 |
| 开发 | 设计定稿 | `index.html` + `dev_log.md` | 功能完成 + 自测通过 |
| 测试 | 开发自测通过 | `test.md`（用例 + 报告） | 测试通过，用户确认 |
| 上线 | 测试通过 | `release.md` | 用户验收通过 → 版本闭环 |

- 状态枚举：`需求` / `设计` / `开发` / `测试` / `上线` / `已闭环`，记录在 `project_memory.md` 顶部。
- **「确认」的形式**：用户必须显式确认（如「OK」「可以进入下一阶段」「设计定稿」）。闲聊式「看着挺好」不构成阶段门禁解锁。
- 小改动也走完五阶段，深度按体量缩放，但状态行必须更新。
- 若当前阶段产物缺失或未确认，AI 必须主动提示：「上一阶段（X）尚未确认，请确认后再继续」，并停止推进。

---

## 五、命名规范

- 文档：固定语义名（`project_memory.md` / `plan.md` / `design.md` / `dev_log.md` / `test.md` / `release.md`），不加日期前缀。
- 版本号：`V{主}.{次}.{修订}`；架构性变化升主，功能新增升次，文字/视觉修订升修订。
- 交付物：`index.html` 为唯一入口文件；如需附加资源，置于同目录 `assets/`。
- 命名规则未经用户确认不得修改。

---

## 六、强制约束

1. 上一阶段未确认，禁止进入下一阶段。
2. 单文件交付是硬约束：新增外部依赖、外部字体、外部图片/接口，必须先经用户确认。
3. 生成代码必须带函数级中文注释。
4. 关键决策必须写入 `project_memory.md`，不得只存在于对话中。
5. 规则调整必须经用户确认，并追加修订记录。
6. 演示路径必须可在断网状态下完成。

---

## 七、规则自我审计

- 每个阶段准出前，AI 自审：是否满足该阶段的准入/准出条件、产物是否已归档。
- 用户指出违规时，AI 立即：① 承认违规；② 修复当前问题；③ 在 `project_memory.md` 踩坑区记录，防止再犯。
